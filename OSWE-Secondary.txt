820234338: You are reviewing a production incident in a Flask + SQLAlchemy application that manages a self-referential many-to-many “followers” relationship between users.
The system was extended to support multi-tenant sharding and Redis caching for follower counts. Each tenant has its own PostgreSQL shard but shares Redis and Celery infrastructure.
After deployment, users reported inconsistent follower counts, cross-tenant relationships, and data drift between database and cache layers.

The followers relationship is defined as:

followers = db.Table(
    'followers',
    db.Column('follower_id', db.Integer, db.ForeignKey('user.id')),
    db.Column('followed_id', db.Integer, db.ForeignKey('user.id'))
)


Each User model includes a tenant_id field, but the relationship table lacks this constraint.
As a result, users from different tenants can follow each other, violating isolation.
Redis caching further amplifies this issue because cached data expires inconsistently across shards.

You must analyze the incident and refactor the design to guarantee cross-tenant integrity, transactional safety, and cache consistency under concurrency.

Tasks

Schema Hardening

Add a composite uniqueness constraint (tenant_id, follower_id, followed_id).

Add tenant_id column to followers and propagate it through ORM relationships.

Enforce same-tenant validation via an after_flush hook.

Transaction Isolation

Replace global commits with shard-aware session management.

Implement retry logic for IntegrityError and deadlocks.

Support cross-shard atomic commits using a distributed transaction coordinator.

Cache Consistency

Introduce distributed locking (e.g., Redlock) to prevent duplicate cache writes.

Periodically verify Redis follower counts against PostgreSQL.

Soft Delete Synchronization
