820234338: You are reviewing a production incident in a Flask + SQLAlchemy application that manages a self-referential many-to-many “followers” relationship between users.
The system was extended to support multi-tenant sharding and Redis caching for follower counts. Each tenant has its own PostgreSQL shard but shares Redis and Celery infrastructure.
After deployment, users reported inconsistent follower counts, cross-tenant relationships, and data drift between database and cache layers.

The followers relationship is defined as:

followers = db.Table(
    'followers',
    db.Column('follower_id', db.Integer, db.ForeignKey('user.id')),
    db.Column('followed_id', db.Integer, db.ForeignKey('user.id'))
)


Each User model includes a tenant_id field, but the relationship table lacks this constraint.
As a result, users from different tenants can follow each other, violating isolation.
Redis caching further amplifies this issue because cached data expires inconsistently across shards.

You must analyze the incident and refactor the design to guarantee cross-tenant integrity, transactional safety, and cache consistency under concurrency.

## Key design changes (summary)
1. Schema hardening
   - followers table now includes:
     - id (pk), tenant_id (not null), follower_id, followed_id, deleted (soft delete).
     - Unique constraint: (tenant_id, follower_id, followed_id) to prevent duplicates and cross-tenant linking.
   - User table includes tenant_id (indexed) and soft-delete boolean.
   - ORM relationship join conditions include tenant scoping and filter out soft-deleted follower rows.

2. Transaction isolation and resiliency
   - `ShardSession` context manager obtains a session for a given tenant's shard and retries commits on IntegrityError/OperationalError with backoff.
   - `TwoPhaseCoordinator` is a naive prepare/commit coordinator for tests to simulate atomic commits across multiple shard sessions. (Note: For production, replace with a robust coordinator or design that avoids cross-shard distributed transactions — e.g., a transactional outbox, compensation, or centralized coordinator).

3. Cache consistency
   - `VersionedFollowerCache` stores follower counts with version numbers so cache updates are applied deterministically.
   - `RedisLock` provides a simple lock wrapper (Redlock-like) to serialize cache writes. For production, use a battle-tested Redlock library and ensure atomic compare-and-set semantics.

4. Soft-delete synchronization and cleanup
   - Followers have `deleted` boolean; queries exclude deleted rows.
   - drift_monitor.py contains a reconciliation function, and a cleanup job (to be expanded) should periodically delete or purge soft-deleted rows older than a threshold.

5. Testing additions
   - Tests simulate concurrent writes and cross-tenant attempts using sqlite shards for fast local verification.
   - Test harness writes logs to test_run.log per the execution requirements.
